# GS-001 — Sprint Health Dashboard
## EazyBI Implementation Guide

## 1. Purpose

This guide defines how to implement the governed Sprint Health Dashboard in EazyBI without losing sprint-start commitment, scope movement, spillover, blocker exposure, quality signals, or Jira drill-down.

The implementation must preserve the project rule that sprints are never extended. Unfinished committed work is recorded against the sprint in which the commitment was missed and is then moved to the next sprint through normal backlog governance.

---

## 2. Implementation Principles

1. Use one governed KPI definition across Jira, EazyBI, Power BI, and executive reporting.
2. Separate sprint-start commitment from current sprint scope.
3. Preserve issue history required for additions, removals, estimate changes, status changes, and carryover.
4. Prefer story points; use issue count only when estimation is unavailable and label the measure clearly.
5. Never use velocity for individual performance comparison.
6. Keep executive views aggregated; expose issue details only through authorized drill-down.
7. Reconcile every published KPI to Jira evidence within an approved tolerance.

---

## 3. Required Jira Import Configuration

### 3.1 Standard dimensions and measures

Import at minimum:

- Project
- Issue
- Issue Type
- Status
- Resolution
- Priority
- Assignee for authorized operational analysis only
- Reporter only where operationally necessary
- Sprint
- Fix Version
- Component
- Created date
- Resolved date
- Due date
- Story Points
- Time spent and original estimate where required
- Issue links when dependency reporting is enabled

### 3.2 Custom fields

Import the governed equivalents of:

- Functional Group or Team
- Pillar or Product
- Blocked indicator or Flagged
- Blocker reason category
- Dependency owner or dependency category
- Acceptance status
- Quality outcome
- Carryover count, when generated by automation
- Sprint baseline identifier, when generated outside EazyBI
- Sprint-start story points, when captured by automation or an external snapshot process
- Added-to-sprint timestamp
- Removed-from-sprint timestamp
- Scope-change reason

The exact custom-field IDs must be recorded in the data dictionary and must not be embedded undocumented in production MDX.

### 3.3 Change history

Enable issue change history for fields required to reconstruct:

- Sprint membership changes
- Story point changes
- Status transitions
- Resolution changes
- Blocked-state transitions
- Acceptance-state changes

A current issue snapshot alone is not sufficient for commitment reliability or scope stability.

## 4. Recommended Cube Design

Use a governed analytics cube dedicated to delivery and sprint reporting where possible. Avoid loading unrelated high-volume service-management history into the same cube unless the shared use case is approved.

Recommended analytical hierarchy:

```text
Portfolio
  → Program
    → Product / Pillar
      → Functional Group / Team
        → Sprint
          → Epic
            → Issue
```

Recommended time perspectives:

- Sprint start date
- Sprint end date
- Issue created date
- Issue resolved date
- Status transition date
- Scope-change date

For executive sprint reporting, Sprint should be the primary delivery period. Calendar time remains necessary for refresh monitoring and trend analysis.

---

## 5. Sprint Baseline Strategy

### 5.1 Preferred method

Create an immutable sprint-baseline snapshot at sprint start using Jira Automation, an integration service, or the enterprise reporting pipeline. Capture one row per committed issue with:

- Sprint ID
- Issue key
- Baseline timestamp
- Baseline story points
- Baseline issue type
- Baseline team
- Baseline epic
- Baseline status
- Baseline inclusion flag

Import the snapshot into EazyBI as additional data or as governed Jira custom fields where technically appropriate.

### 5.2 Alternative method

When external snapshots are not available, reconstruct sprint membership from Jira changelog data. This approach must be validated carefully because board behavior, parallel sprint membership, reopened sprints, and historical field changes may produce ambiguity.

### 5.3 Prohibited shortcut

Do not calculate commitment reliability from the current list of issues in a closed sprint. This mixes baseline commitment with scope added later and can materially misstate reliability.

## 6. Core Calculated Measures

The examples below are templates. Dimension and measure names must be adapted to the actual EazyBI cube.

### 6.1 Sprint-start committed story points

```mdx
Sum(
  Filter(
    Descendants([Issue].CurrentHierarchyMember, [Issue].[Issue]),
    [Measures].[Sprint baseline included] > 0
  ),
  [Measures].[Sprint baseline story points]
)
```

### 6.2 Completed sprint-start commitment

```mdx
Sum(
  Filter(
    Descendants([Issue].CurrentHierarchyMember, [Issue].[Issue]),
    [Measures].[Sprint baseline included] > 0
    AND [Measures].[Issues resolved] > 0
  ),
  [Measures].[Sprint baseline story points]
)
```

The production implementation must evaluate completion at sprint closure, not merely current resolution state.

### 6.3 Commitment reliability percentage

```mdx
CASE WHEN [Measures].[Sprint-start committed story points] > 0 THEN
  [Measures].[Completed sprint-start commitment]
  /
  [Measures].[Sprint-start committed story points]
END
```

Format as percentage.

### 6.4 Current scope story points

```mdx
[Measures].[Story Points created]
```

Use the measure that correctly reflects issues currently associated with the selected sprint. Validate behavior for issues that have belonged to multiple sprints.

### 6.5 Current scope completion percentage

```mdx
CASE WHEN [Measures].[Current scope story points] > 0 THEN
  [Measures].[Completed current scope story points]
  /
  [Measures].[Current scope story points]
END
```

### 6.6 Added scope percentage

```mdx
CASE WHEN [Measures].[Sprint-start committed story points] > 0 THEN
  [Measures].[Story points added after sprint start]
  /
  [Measures].[Sprint-start committed story points]
END
```

### 6.7 Removed scope percentage

```mdx
CASE WHEN [Measures].[Sprint-start committed story points] > 0 THEN
  [Measures].[Story points removed after sprint start]
  /
  [Measures].[Sprint-start committed story points]
END
```

### 6.8 Scope stability percentage

```mdx
CASE WHEN [Measures].[Sprint-start committed story points] > 0 THEN
  Max(
    0,
    1 - (
      ([Measures].[Story points added after sprint start]
       + [Measures].[Story points removed after sprint start])
      /
      [Measures].[Sprint-start committed story points]
    )
  )
END
```

### 6.9 Spillover rate

```mdx
CASE WHEN [Measures].[Sprint-start committed story points] > 0 THEN
  [Measures].[Incomplete committed story points at sprint end]
  /
  [Measures].[Sprint-start committed story points]
END
```

### 6.10 Blocked remaining scope percentage

```mdx
CASE WHEN [Measures].[Remaining story points] > 0 THEN
  [Measures].[Blocked remaining story points]
  /
  [Measures].[Remaining story points]
END
```

### 6.11 Repeated carryover count

```mdx
Sum(
  Filter(
    Descendants([Issue].CurrentHierarchyMember, [Issue].[Issue]),
    [Measures].[Carryover count] >= 2
  ),
  [Measures].[Issues created]
)
```

### 6.12 Predictability index

Use a governed rolling window, normally the last six completed sprints.

```mdx
Avg(
  Tail(
    Filter(
      [Sprint].[Sprint].Members,
      [Measures].[Sprint closed flag] > 0
    ),
    6
  ),
  [Measures].[Commitment reliability %]
)
-
[Measures].[Reliability variability penalty]
```

The variability penalty must be documented and tested before publication.

## 7. Sprint Health Score

Recommended initial weighting:

```text
Commitment Reliability       30%
Completion Alignment         20%
Scope Stability              15%
Blocked Work Health          15%
Spillover Health             10%
Quality Health               10%
```

Each component must be normalized to 0–100. The score must support critical overrides. For example:

- Critical dependency blocking a release commitment
- Material security or regulatory acceptance failure
- Missing or invalid sprint baseline
- Data freshness outside the approved publication window

A critical override forces the overall status to Red even when the weighted score is otherwise Amber or Green.

## 10. Performance Design

- Use calculated members only where a standard measure cannot satisfy the requirement.
- Avoid repeated large `Descendants` scans in multiple measures; create reusable base measures.
- Limit issue-level rows in executive dashboards.
- Use page filters for sprint, program, team, and project.
- Avoid importing unused custom fields and change history.
- Test reports against production-like data volume.
- Keep rolling trend windows bounded.
- Use precomputed snapshot attributes for expensive baseline logic.
- Review query execution time before release.

Recommended performance target:

- Executive page initial render: under 10 seconds under normal load
- Drill-down report: under 15 seconds for the approved population
- Scheduled import completion: inside the agreed freshness window

---

## 11. Import and Refresh Strategy

### Daily during sprint

- Incremental Jira import
- Baseline integrity check
- Scope-change reconciliation
- Blocker-state update
- Refresh timestamp publication

### At sprint closure

- Final incremental import
- Capture closure status
- Freeze sprint KPI results
- Record spillover against the closed sprint
- Verify moved issues remain traceable

### Failure handling

When import or validation fails:

- Mark freshness as failed or stale
- Suppress executive RAG where the underlying data is unreliable
- Retain the last valid snapshot with a visible timestamp
- Log the failure and assigned owner
- Prevent silent publication of partial data

---

## 12. Data Validation

Validate the following for every sprint:

- Baseline issue count and story points match the approved sprint-start snapshot.
- Current sprint population reconciles with Jira.
- Added and removed scope reconcile with history.
- Completed baseline scope is evaluated at sprint closure.
- Spillover is not erased after issues move to the next sprint.
- Story point changes do not overwrite baseline estimates.
- Subtasks are not double-counted when parent-level reporting is used.
- Cancelled and out-of-scope items follow the approved exclusion rule.
- Closed sprint dates match Jira.
- Executive views contain no prohibited fields.

Recommended reconciliation tolerance:

- Zero variance for issue count where deterministic
- Zero variance for baseline story points
- Documented exceptions only for known Jira or import limitations

---

## 13. Security and Distribution

EazyBI access must align with Jira and enterprise reporting authorization.

- Do not publish email, phone, employee ID, customer identifiers, credentials, or secrets.
- Avoid assignee names in broadly shared executive views.
- Use team-level aggregation by default.
- Restrict source-data export.
- Validate issue-level drill-down permissions.
- Exclude free-text comments and descriptions from the default cube unless specifically approved.
- Maintain separate executive-safe and operational reports when required.

## 14. Troubleshooting

| Symptom | Likely Cause | Corrective Action |
|---|---|---|
| Commitment equals current scope | Baseline not captured | Implement immutable sprint-start snapshot |
| Closed sprint results change later | Current issue state used instead of closure state | Freeze closure snapshot or use historical status |
| Spillover becomes zero after issue moves | Metric tied only to current sprint membership | Attribute miss to original committed sprint |
| Scope stability exceeds 100% or becomes negative | Incorrect denominator or unbounded formula | Use baseline denominator and bound 0–100% |
| Story point totals differ from Jira | Multiple sprint membership, subtasks, or import settings | Reconcile issue population and hierarchy rules |
| Dashboard is slow | Excessive issue-level MDX or unbounded history | Precompute baseline fields and reduce row cardinality |
| Blocked count is incomplete | Multiple blocker representations | Normalize status, Flagged, label, and custom field rules |
| Unauthorized issue text appears | Free-text field imported or broad access | Remove field and tighten report permissions |

## 16. Definition of Done

The EazyBI implementation is complete only when:

- Sprint-start commitment is preserved immutably.
- Current scope and baseline scope are visibly separate.
- Scope additions, removals, estimate changes, blockers, and spillover are auditable.
- All KPI formulas match the GS-001 KPI Catalog.
- Executive and operational views use the same governed logic.
- Results reconcile to Jira and the approved snapshot source.
- Performance meets the agreed service target.
- Restricted data is absent from unauthorized views.
- Every visual supports interpretation, action, and drill-down.
